1. INTRODUCTION
===============================================================================


1.1 Background
-------------------------------------------------------------------------------

[RETRO-FRAME] is a Retro-Endeavor that provides [COMMON DOCUMENTATION] (i.e.
definitions, guidelines, templates and generic specifications) as well as
topic-related specifications (covered by individual repositories like this
one related to data format specifications) which are intended for use in
retrospective programming and may be used as a whole or partially for other
purposes.

The Retro-Frame Data Format Specifications comprise binary and text data
formats which may be implemented by a program (e.g. as file formats) and may
be used by other specifications.


1.2 Scope
-------------------------------------------------------------------------------

This document specifies the Retro System Specification (RSS) data format of the
type "RSS" which may be used to specify the full behavior of systems and their
components (e.g. CPU, RAM or a keyboard). It is intended that systems which are
specified in this way can be emulated.

2. OVERVIEW
===============================================================================

We undertake the very challenging task to provide a specification format which
allows to specify computer systems including their components so accurately
that they can be emulated soley based on that specification.

Although the focus is on retro systems, any system may be specified by the RSS
format as long as all relevant features are covered.

The RSS format provides a simple import mechanism which allows re-use of parts
of the entire specification (e.g. a CPU which is specified by one RSS format
and may be used by RSS formats of different systems which use that CPU).

Paths in a RSS format (e.g. for an import) are represented by universal paths
(see [COMMON DOCUMENTATION], /spec/rf-path.txt//).



3. BASIC CONCEPTS
===============================================================================


3.1 Systems, components and buses
-------------------------------------------------------------------------------

A system is a set of components (in no particular order) which may be connected
by one or more buses. There may be multiple instances of the same component (it
depends on the capabilities of those components to behave differently). Systems
are identified by a label.

Each component ma



The actual buses of a system are specified if they occur in the <rss-bus-list>
of a <rss-system-component>. A bus must match the name and data bit length. The
<rss-bus-list> of a component <rss-block-header> specifies the buses used by
this component. However, the acutal assignment of such a bus is done by the
<rss-bus-list> of a <rss-system-component> by position (a hypen '-' indicates
that a bus provided by a component is not used). The number of data bits must
match at the position.

Example:

  ROM "ROM" (MEM/8, PORT/8) [...]

  KEYBOARD "Keyboard" (PORT/4) [...]

  DEVICE "Port mapper" (PORT/4, PORT/8) [...]

  CPU "CPU" (ROM/8, INT, PORT/4) [...]

  SYSTEM "SYS123"
  {
      ROM "ROM" (ROM/8, PORT/8).  ; ROM/8 becomes MEM/8 within the component

      KEYBOARD "KBD" (PORT/4).  ; bus PORT/4 is different from bus PORT/8

      DEVICE "Port mapper" (PORT/4, PORT/8).

      CPU "CPU" (ROM/8, -, PORT/4).  ; non-data INT bus is not used
  }

3.1 Keyboard
-------------------------------------------------------------------------------

As modern keyboards may differ from the retro system keyboard, one of the most
challenging aspects of retro system emulation is the keyboard input.

The basic concept of the RSS format in terms of keyboards is that a component
(usually a KEYBOARD component) may specify arbitrary keys with individual codes
(using the $KEY statement in the initialization section) and emulated events on
those keys result in KEY PRESSED <key code> and KEY RELEASED <key code> events
which may be handled by that component.

Example:

  KEYBOARD "Minimal Keyboard" (BUS/1)
  {
      $KEY(0).  ; specify key with key code 0
      $KEY(1).  ; specify key with key code 1
      $KEY(3).  ; specify key with key code 3 - key code 2 is unused

  KEY PRESSED nn:

      BUS/1(UINT/2(n)) = 1.  ; send 1 to BUS/1 using the key code as address

  KEY RELEASED nn:

      BUS/1(UINT/2(n)) = 0.  ; send 0 to BUS/1 using the key code as address
  }

The actual source of a keyboard event depends on the emulator. However, the
$KEY, $KEY_MODIFIER and $KEY_LOCKABLE statements provides additional attributes
which may be used by an emulator:

- $KEY specifies a normal key.

- $KEY_MODIFIER specifies a modifier key (e.g. SHIFT or ALT) which is intended
  to be held down (i.e. pressed) until a non-modifier key is pressed (note that
  multiple modifier keys may be held down at the same time). An emulator may
  send KEY RELEASED events for all keys which were held down after the non-
  modifier key is released.

- $KEY_LOCKABLE specifies a key with two different states (active and inactive)
  which are switched each time the key is pressed. Although the actual behavior
  of such keys is implemented by the system, an emulator may indicate the state
  (while treating the key like a normal key otherwise).

All key specification statements expect the key code as the first parameter,
followed by an optional sequence of one or more emulator keys which will be
mapped to the specified keys. An emulator key may be one of the following:

- A character literal ( "'" <character "'" ).

- A Latin-1 codepoint value (0x00..0xFF).

- A predefined key constant:

  - The following predefined key constants may be expected to have related keys
    on each modern system:

    SPACE, BACKSPACE, TAB, RETURN, ESCAPE, L_SHIFT, R_SHIFT, CAPS_LOCK, CTRL,
    CURSOR_UP, CURSOR_DOWN, CURSOR_LEFT, CURSOR_RIGHT, CURSOR_PAGE_UP,
    CURSOR_PAGE_DOWN, CURSOR_HOME, CURSOR_END, F1..F12 (function keys),
    FUNCTION (Fn key).

  - The following predefined key constants may be expected to have related keys
    if the keyboard has a numeric keypad:

    ENTER, NUMPAD_UP, NUMPAD_DOWN, NUMPAD_LEFT, NUMPAD_RIGHT, NUMPAD_PAGE_UP,
    NUMPAD_PAGE_DOWN, NUMPAD_HOME, NUMPAD_END, NUMPAD_CENTER (i.e. the '5' key
    on the numeric keypad), NUMPAD_DECIMAL, NUMPAD_ADD, NUMPAD_SUB, NUMPAD_DIV,
    NUMPAD_MUL.

  - The following predefined key constants may be expected to have mapped keys
    or combination of keys:

    CANCEL (CTRL + 'C' or Break key), META (Alt or Option key), SUPER (Windows
    or Command key).

  - The following predefined key constants are defined but there may be no
    releated key present on the keyboard:

    PRINT, SYS_REQ, PAUSE, SCROLL_LOCK, NUM_LOCK, HELP, MENU, INSERT, DELETE,
    NUMPAD_EQUALS, NUMPAD_COMMA, F13..F24.



4. TEXT DATA FORMAT
===============================================================================


4.1 Characteristics and character processing
-------------------------------------------------------------------------------

RSS is a not self-delimiting text format using the STANDARD CHARACTER SET.

On input, NUL characters shall be ignored but other control characters except
whitespace (including line breaks) shall be considered invalid. On output, NUL
characters should be avoided.

The following tokens are used:

- A decimal number in the range 0x00000000.. 0xFFFFFFFF, consisting of a
  sequence of up to 32 decimal digits.
- A hexadecimal number in the range 0x00000000.. 0xFFFFFFFF, consisting of a
  sequence of up to 32 hexadecimal digits ('A'..'F' may be upper- or lowercase)
  trailed by the letter 'H' (may be upper- or lowercase).
- An identifier of up to 32 characters. Lowercase letters shall implicitly be
  converted to uppercase letters. Note that identifiers may start with a digit.
- A string, enclosed in double-quotes, of up to 255 characters (excluding the
  double-quoted). No line break shall occur in a string. Escape character is
  the reverse solidus ('\'). Currently, only the double-quotes are defined as
  an escape sequence.
- The following symbols: ",", ".", ":", "+", "-", "*", "/", "%", "==", "!=",
  "<", "<=", ">", ">=", "<>", "=", "+=", "-=", "*=", "/=", "%=", "&=", "|=",
  "^=", "&", "|", "^", "~", "&&", "||", "^^", "!", "?", "<<", "<<<", ">>",
  ">>>", "(", ")", "[", "]", "{" and "}".

Two consecutive identifiers must be separated by whitespace if the leading
identifier does not have a trailing single-quote ''' and the successing
identifier does not have a leading dollar-sign '$'. Symbols which consist of
more than one character are parsed in a way that alwayse the longest token is
recognized (e.g. "<<=" is parsed as "<<" and "=" rather than "<" and "<=").

There are no restrictions on the format version.


4.2 Syntax of version 1.0
-------------------------------------------------------------------------------

<rss-format-identifier>:

  "RSS/1.0"

<rss-ws>:

  ( WS | [ ";" [ . | WS ]* ] LB )*

<rss-dec-number>:

  9 [_9 ]*

<rss-hex-number>:

  ( X_)*_"H"

<rss-bit>:

  "0" | "1" | A

<rss-bit-mask>:

  <rss-bit> [_<rss-bit> ]*

<rss-string-escape>:

  """"

<rss-string>:

  """"_[_._|_"\"_<rss-string-escape>_|_WS_]* """"

<rss-label>:

  <rss-string>

<rss-identifier>:

  ( "$" | A | 9 | "_" ) [_A |_9 |_"_" ]* [ "'" ]

<rss-import>:

  "IMPORT" <universal-path> "."

<rss-data-bus>:

  <rss-identifier> "/" <rss-number>

<rss-non-data-bus>:

  <rss-identifier>

<rss-bus>:

  <rss-data-bus> | <rss-non-data-bus>

<rss-bus-list>:

  "(" <rss-bus> [ "," <rss-bus> ]* ")"

<rss-block-header>:

  <rss-label> [ <rss-bus-list> ]

<rss-opcode-event>:

  "OPCODE" [ <rss-bit-mask> ]*

<rss-key-event>:

  "KEY" [ "PRESSED" | "RELEASED" ] [ <rss-bit-mask> ]*

<rss-bus-event>:

  <rss-identifier> [ "READ" | "WRITE" ] [ <rss-bit-mask> ]

<rss-standard-event>:

  "RESET" | <rss-bus-event>

<rss-cpu-event>:

  <rss-standard-event> | <rss-opcode-event>

<rss-cpu-section>:

  <rss-cpu-event> ":" [ <rss-statement> ]*

<rss-cpu>:

  "CPU" <rss-block-header> "{" [ <rss-cpu-section> ]* "}"

<rss-rom-section>:

  <rss-standard-event> ":" [ <rss-statement> ]*

<rss-rom>:

  "ROM" <rss-block-header> "{" [ <rss-rom-section> ]* "}"

<rss-ram-section>:

  <rss-standard-event> ":" [ <rss-statement> ]*

<rss-ram>:

  "RAM" <rss-block-header> "{" [ <rss-ram-section> ]* "}"

<rss-keyboard-event>:

  <rss-standard-event> | <rss-key-event>

<rss-keyboard-section>:

  <rss-keyboard-event> ":" [ <rss-statement> ]*

<rss-keyboard>:

  "KEYBOARD" <rss-block-header> "{" [ <rss-keyboard-section> ]* "}"

<rss-screen-section>:

  <rss-standard-event> ":" [ <rss-statement> ]*

<rss-screen>:

  "SCREEN" <rss-block-header> "{" [ <rss-screen-section> ]* "}"

<rss-component>:

  <rss-block-header> "{" [ <rss-component-section> ]* "}"

<rss-component-type>:

  "CPU" | "ROM" | "RAM" | "KEYBOARD" | "SCREEN"

<rss-system-component>:

  <rss-component-type> <rss-label> [ <rss-bus-list> ] "."

<rss-system>:

  "SYSTEM" <rss-label> "{" [ <rss-system-component> ]* "}"

<rss-body>:

  [ <rss-import> | <rss-component> | <rss-system> ]*

<rss-header>:

  [ <rf-skip-element>_]* ( LB | "??" )

<rss>:

  <rss-format-identifier>_<rss-header>_<rss-body>
