1. INTRODUCTION
===============================================================================


1.1 Background
-------------------------------------------------------------------------------

[RETRO-FRAME] is a Retro-Endeavor that provides [COMMON DOCUMENTATION] (i.e.
definitions, guidelines, templates and generic specifications) as well as
topic-related specifications (covered by individual repositories like this
one related to data format specifications) which are intended for use in
retrospective programming and may be used as a whole or partially for other
purposes.

The Retro-Frame Data Format Specifications comprise binary and text data
formats which may be implemented by a program (e.g. as file formats) and may
be used by other specifications.


1.2 Scope
-------------------------------------------------------------------------------

This document specifies the System Specification for Emulation (SSE) data
format of the type "SSE" which may be used to specify the full behavior of
systems and their components (e.g. CPU, RAM or a keyboard). It is intended
that systems which are specified in this way can be emulated.

-------------------------------------------------------------------------------

2. OVERVIEW
===============================================================================

The SSE format is intended to provide to specifications of computer systems
including their components so accurately that they can be emulated soley based
on that specification. Although the focus is on retro systems, any system may
be specified by the SSE format as long as all relevant features are covered.

The SSE format provides a simple import mechanism which allows re-use of parts
of the entire specification (e.g. a CPU which is specified by one SSE format
and may be used by other SSE formats for several systems which use that CPU).

All paths in the SSE format (e.g. for an import) are represented by relative
universal paths (see [COMMON DOCUMENTATION], /spec/rf-path.txt//). Connecting
path references may be used to distinguish different base paths which must be
specified by the implementation (e.g. "SSE:" prefix for includes or ("FLOPPY:"
prefix for floppy disk images).



3. BASIC CONCEPTS
===============================================================================


3.1 Systems, components and buses
-------------------------------------------------------------------------------

A system is a set of components (in no particular order) which may be connected
by one or more buses. There may be multiple instances of the same component (it
depends on the capabilities of those components to behave differently). Systems
are identified by a label.

Each component ma



The actual buses of a system are specified if they occur in the <sse-bus-list>
of a <sse-system-component>. A bus must match the name and data bit length. The
<sse-bus-list> of a component <sse-block-header> specifies the buses used by
this component. However, the acutal assignment of such a bus is done by the
<sse-bus-list> of a <sse-system-component> by position (a hypen '-' indicates
that a bus provided by a component is not used). The number of data bits must
match at the position.

Example:

  ROM "ROM" (MEM/8, PORT/8) [...]

  KEYBOARD "Keyboard" (PORT/4) [...]

  DEVICE "Port mapper" (PORT/4, PORT/8) [...]

  CPU "CPU" (ROM/8, INT, PORT/4) [...]

  SYSTEM "SYS123"
  {
      ROM "ROM" (ROM/8, PORT/8).  ; ROM/8 becomes MEM/8 within the component

      KEYBOARD "KBD" (PORT/4).  ; bus PORT/4 is different from bus PORT/8

      DEVICE "Port mapper" (PORT/4, PORT/8).

      CPU "CPU" (ROM/8, -, PORT/4).  ; non-data INT bus is not used
  }

4. KEYBOARDS
===============================================================================

As modern keyboards differ from most original retro system keyboards, the SSE
format provides specifications which allow emulation of a keyboard.


4.1 Basic concept
-------------------------------------------------------------------------------

The basic concept in terms of keyboards is that a component, usually of but not
limited to KEYBOARD type, may specify arbitrary keys with individual <codes>
using the $KEY, $KEY_MODIFIER or $KEY_LOCKABLE statement (see chapter 4.2) in
the initialization section. Each key, when pressed or released, will raise a
KEY PRESSED <code> respective KEY RELEASED <code> event which may be handled
within that component.

Example:

  KEYBOARD "Example keyboard (3 keys)" (BUS/1)
  {
      $KEY(0).          ; specify key with key code 0
      $KEY(1).          ; specify key with key code 1
      $KEY_MODIFIER(3). ; specify key with key code 3 (key code 2 is unused)

  KEY PRESSED nn:

      BUS/1(UINT/2(n)) = 1. ; send 1 to BUS/1 using the key code as the address

  KEY RELEASED nn:

      BUS/1(UINT/2(n)) = 0. ; send 0 to BUS/1 using the key code as the address
  }

The actual sources of keyboard events depend on the emulator. In general, the
following two options may be used:

- The same or a similar key is pressed or released on the physical keyboard. In
  order to achieve mapping, abstract keys may be assigned to emulated keys (see
  chapter 4.2).

- An image of the emulated keyboard may be shown on the actual screen (virtual
  keyboard) and the keys on that image may be "pressed" using a mouse or other
  input device of the actual system (including customized mappings to keys on
  the physical keyboard). A map of the keyboard image may be specified in order
  to assign regions of the image to emulated keys (see chapter 4.3).


4.2 Key specifications
-------------------------------------------------------------------------------

The $KEY, $KEY_MODIFIER and $KEY_LOCKABLE statements specify different classes
of keys:

- $KEY specifies a normal key.

- $KEY_MODIFIER specifies a modifier key (e.g. SHIFT or ALT) which is intended
  to be held down (i.e. pressed) until a non-modifier key is pressed (note that
  multiple modifier keys may be held down at the same time). An emulator may
  send automatic KEY RELEASED events for all modifier keys which were held down
  immediately after a non-modifier key is pressed. The number of modifier keys
  is limited to 32.

- $KEY_LOCKABLE specifies a key with two different states (active and inactive)
  which are switched each time the key is pressed. Although the actual behavior
  of such keys is implemented by the system, an emulator may indicate the state
  (e.g. by a virtual LED) while treating the key like a normal key otherwise.
  The number of lockable keys is limited to 32.

All key specification statements expect the key code as the first parameter,
optionally followed by a sequence of one or more abstract keys which will be
assigned to the specified key. An abstract key may be one of the following:

- A value of a Retro-Frame character codepoint in the range 0x000000..0xFFFFFF
  which represents the key (see [COMMON DOCUMENTATION], /spec/rf-char.txt//).
  Although a wide range of characters may be specified, it is recommended to
  use this representation of abstract keys only for Latin-1 codepoints which
  are neither ASCII nor control characters and thus in the range R+00A0..R+00FF
  (use predefined key constants for control characters and character literals
  for the range R+0020..R+007E instead).

- A character literal "'" <character "'" which is (as usual) equivalent to the
  corresponding ASCII value and thus the Retro-Frame character codepoint.

- A predefined key constant:

  - The following predefined key constants may be expected to have related keys
    on each modern system:

    SPACE, BACKSPACE, TAB, RETURN, ESCAPE, L_SHIFT, R_SHIFT, CAPS_LOCK, CTRL,
    CURSOR_UP, CURSOR_DOWN, CURSOR_LEFT, CURSOR_RIGHT, CURSOR_PAGE_UP,
    CURSOR_PAGE_DOWN, CURSOR_HOME, CURSOR_END, F1..F12 (function keys),
    FUNCTION (Fn key).

  - The following predefined key constants may be expected to have related keys
    if the keyboard has a numeric keypad:

    ENTER, NUMPAD_UP, NUMPAD_DOWN, NUMPAD_LEFT, NUMPAD_RIGHT, NUMPAD_PAGE_UP,
    NUMPAD_PAGE_DOWN, NUMPAD_HOME, NUMPAD_END, NUMPAD_CENTER (i.e. the '5' key
    on the numeric keypad), NUMPAD_DECIMAL, NUMPAD_ADD, NUMPAD_SUB, NUMPAD_DIV,
    NUMPAD_MUL.

  - The following predefined key constants may be expected to have mapped keys
    or combination of keys:

    CANCEL (CTRL + 'C' or Break key), META (Alt or Option key), SUPER (Windows
    or Command key).

  - The following predefined key constants are defined but there may be no
    releated key present on the keyboard:

    PRINT, SYS_REQ, PAUSE, SCROLL_LOCK, NUM_LOCK, HELP, MENU, INSERT, DELETE,
    NUMPAD_EQUALS, NUMPAD_COMMA, F13..F24.

Instead of simply specifying an abstract key in that way, the pseudo-function
MODIFIED may be used to assign an abstract key to an emulated key having one
or more modifier keys pressed implicitly. The abstract key is expected as the
first parameter while one or more key codes of previously specified modifier
keys follow.

Example:

  $KEY_LOCKABLE(0x10, CAPS_LOCK).
  $KEY_MODIFIER(0x11, L_SHIFT, R_SHIFT).
  $KEY_MODIFIER(0x12, CTRL).
  $KEY_MODIFIER(0x13, META).
  $KEY(0x20, '0').
  $KEY(0x21, '1', MODIFIED('!', 0x11)).
  $KEY(0x22, '2', MODIFIED('\"', 0x11)).
  $KEY(0x23, '3', MODIFIED('#', 0x11)).
  $KEY(0x30, 'q', MODIFIED('Q', 0x10), MODIFIED('@', 0x12, 0x13)).
  $KEY(0x30, 'w', MODIFIED('W', 0x10)).
  $KEY(0x40, RETURN, ENTER).


4.3 Key images and maps
-------------------------------------------------------------------------------

In order to visually represent the keyboard, up to 4 images may be specified by
the $KEYBOARD_IMAGE statement:

- The first image must always be present and shows all keys released while the
  lockable keys are inactive. This is the default image of the keyboard.

- The second (optional) image shows all keys pressed while the lockable keys
  are inactive. If given, this image is used to represent pressed keys unless
  a locked key becomes active and the fourth image (see below) is given. In
  addition, this image is used to represent released active lockable keys if
  the third image (see below) is not given.

- The third (optional) image shows all keys released while the lockable keys
  are active.

- The fourth (optional) image shows all keys pressed while the lockable keys
  are active.

The keyboard image may be used for key events if key mapping is given be one or
more $KEYBOARD_MAP statements. Such a statement expects one or more strings
which draw the map using hexadecimal values (without any prefix) to represent
the key codes and the hypen '-', the vertial bar '|' and the plus sign '+' to
represent the boundaries of the individual key (i.e. each value should be
surrounded by those characters). While an appropriate use of those characters
may help to make the map more visible, they are equivalent on evaluation.

Example:

  $KEYBOARD_MAP(
      "+---+---+",
      "|000|001|",
      "++--+- ++",
      " | 003 |",
      " +-----+").

The maximum length of those strings determine the number of virtual columns + 1
while the number of strings determine the number of virtual rows + 1 (thus, in
the example above, there are 8 columns and 4 rows). The width and height of the
bitmap, in pixels, should be a multiple of the number of columns respective
rows.



5. TEXT DATA FORMAT
===============================================================================


5.1 Characteristics and character processing
-------------------------------------------------------------------------------

SSE is a not self-delimiting text format using the STANDARD CHARACTER SET.

On input, NUL characters shall be ignored but other control characters except
whitespace (including line breaks) shall be considered invalid. On output, NUL
characters should be avoided.

The following tokens are defined:

- Symbol

 ",", ".", ":", "+", "-", "*", "/", "%", "==", "!=",
  "<", "<=", ">", ">=", "<>", "=", "+=", "-=", "*=", "/=", "%=", "&=", "|=",
  "^=", "&", "|", "^", "~", "&&", "||", "^^", "!", "?", "<<", "<<<", ">>",
  ">>>", "(", ")", "[", "]", "{" and "}".
- A string, enclosed in double-quotes, of up to 127 characters (excluding the
  double-quotes). No line break shall occur in a string. Escape character is
  the reverse solidus ('\'). Currently, only the double-quotes are defined as
  an escape sequence.
- A binary, decimal or hexadecimal number in the range 0x00000000.. 0xFFFFFFFF.
  Leading zeros are ignored. Binary numbers are prefixed by "0b" or "0B" while
  hexadecimal numbers are prefixed by "0x" or "0X". The total length of a number
  token is 63 characters and numbers must be separated from other 
- An identifier of up to 32 characters. Lowercase letters shall implicitly be
  converted to uppercase letters. Note that identifiers may start with a digit.

Two consecutive identifiers must be separated by whitespace if the leading
identifier does not have a trailing single-quote ''' and the successing
identifier does not have a leading dollar-sign '$'. Symbols which consist of
more than one character are parsed in a way that alwayse the longest token is
recognized (e.g. "<<=" is parsed as "<<" and "=" rather than "<" and "<=").

There are no restrictions on the format version.


5.2 Syntax of version 1.0
-------------------------------------------------------------------------------

<sse-format-identifier>:

  "SSE/1.0"

<sse-ws>:

  ( WS | [ ";" [ . | WS ]* ] LB )*

<sse-dec-number>:

  9 [_9 ]*

<sse-hex-number>:

  ( X_)*_"H"

<sse-bit>:

  "0" | "1" | A

<sse-bit-mask>:

  <sse-bit> [_<sse-bit> ]*

<sse-string-escape>:

  """"

<sse-string>:

  """"_[_._|_"\"_<sse-string-escape>_|_WS_]* """"

<sse-label>:

  <sse-string>

<sse-identifier>:

  ( "$" | A | 9 | "_" ) [_A |_9 |_"_" ]* [ "'" ]

<sse-import>:

  "IMPORT" <universal-path> "."

<sse-data-bus>:

  <sse-identifier> "/" <sse-number>

<sse-non-data-bus>:

  <sse-identifier>

<sse-bus>:

  <sse-data-bus> | <sse-non-data-bus>

<sse-bus-list>:

  "(" <sse-bus> [ "," <sse-bus> ]* ")"

<sse-block-header>:

  <sse-label> [ <sse-bus-list> ]

<sse-opcode-event>:

  "OPCODE" [ <sse-bit-mask> ]*

<sse-key-event>:

  "KEY" [ "PRESSED" | "RELEASED" ] [ <sse-bit-mask> ]*

<sse-bus-event>:

  <sse-identifier> [ "READ" | "WRITE" ] [ <sse-bit-mask> ]

<sse-standard-event>:

  "RESET" | <sse-bus-event>

<sse-cpu-event>:

  <sse-standard-event> | <sse-opcode-event>

<sse-cpu-section>:

  <sse-cpu-event> ":" [ <sse-statement> ]*

<sse-cpu>:

  "CPU" <sse-block-header> "{" [ <sse-cpu-section> ]* "}"

<sse-rom-section>:

  <sse-standard-event> ":" [ <sse-statement> ]*

<sse-rom>:

  "ROM" <sse-block-header> "{" [ <sse-rom-section> ]* "}"

<sse-ram-section>:

  <sse-standard-event> ":" [ <sse-statement> ]*

<sse-ram>:

  "RAM" <sse-block-header> "{" [ <sse-ram-section> ]* "}"

<sse-keyboard-event>:

  <sse-standard-event> | <sse-key-event>

<sse-keyboard-section>:

  <sse-keyboard-event> ":" [ <sse-statement> ]*

<sse-keyboard>:

  "KEYBOARD" <sse-block-header> "{" [ <sse-keyboard-section> ]* "}"

<sse-screen-section>:

  <sse-standard-event> ":" [ <sse-statement> ]*

<sse-screen>:

  "SCREEN" <sse-block-header> "{" [ <sse-screen-section> ]* "}"

<sse-component>:

  <sse-block-header> "{" [ <sse-component-section> ]* "}"

<sse-component-type>:

  "CPU" | "ROM" | "RAM" | "KEYBOARD" | "SCREEN"

<sse-system-component>:

  <sse-component-type> <sse-label> [ <sse-bus-list> ] "."

<sse-system>:

  "SYSTEM" <sse-label> "{" [ <sse-system-component> ]* "}"

<sse-body>:

  [ <sse-import> | <sse-component> | <sse-system> ]*

<sse-header>:

  [ <rf-skip-element>_]* ( LB | "??" )

<sse>:

  <sse-format-identifier>_<sse-header>_<sse-body>


5.3 Semantics
-------------------------------------------------------------------------------
