3. DEFLATE STAGES
===============================================================================


3.1 Identifying identical sequences (LZ77 analysis)
-------------------------------------------------------------------------------

The initial processing of the input data (given as a UINT-8 sequence of bytes)
is an algorithm which identifies identical sequences of a length from 3 to 258
bytes within a sliding window of 32768 bytes according to the LZ77 compression
(Lempel-Ziv 1977, the algorithms are not subject to this description of the
data format):

                          +------------------------------+
                          |  32768 bytes sliding window  |
  +-----------------------+------------------------------+------------------+
  |  input data (UINT-8)                 <length>         <length>          |
  +--------------------------------------^----------------^-----------------+
                                         |    distance    | current index
                                         +----------------+

The position of the identical sequence within the sliding window is referenced
by the backward distance relative to the current index (i.e. the byte preceding
the current index has distance 1 and the maximum distance is 32768). Within the
first 32768 bytes of the input data, the sliding window must be clipped (i.e.
the distance must not exceed the input data). While the sequence must start
within the sliding window, it may overlap with the identical sequence starting
from the current index.

All references to identical sequences, given by the triple

  (index, distance, length)

are intermediate information at this stage and may be stored at discretion. No
more than one reference shall exist for each index. If more than one sequence
was found in the sliding window, the longest sequence should be chosen (if the
maximum length was found multiple times, the smallest distance should be
favored).

Example:

  index  input data (hex)  distance  length  comment
  -----  ----------------  --------  ------  --------------------------------
      0                00       n/a     n/a  identical sequence not possible
      1                01       n/a     n/a  no identical sequence
      2                AA       n/a     n/a  no identical sequence
      3                BB       n/a     n/a  no identical sequence
      4                00       n/a     n/a  sequence 00 01 is too short
      5                01       n/a     n/a  sequence 01 is too short
      6                AF       n/a     n/a  no identical sequence
      7                00         3       5  sequence 00 01 AF 00 01 overlaps
      8                01       n/a     n/a  part of identical sequence
      9                AF       n/a     n/a  part of identical sequence
     10                00       n/a     n/a  part of identical sequence
     11                01       n/a     n/a  part of identical sequence
     12                BE       n/a     n/a  no identical sequence
     13                00         6       3  favor smaller distance
     14                01       n/a     n/a  part of identical sequence
     15                AF       n/a     n/a  part of identical sequence
     16                FF       n/a     n/a  no identical sequence

  As a result, the identical sequences are (7, 3, 5) and (13, 6, 3).

Note that LZ77 compression is always performed on the entire input data, even
if the data is processed in smaller buffers and regardless of the block format
determined later (see chapter 3.4). However, no references to other input data
must be used, even if other input data immediately preceding may be given (e.g.
in a file).

On compression, in order to comply with the data format, it is not required to
find all or the optimal identical sequences (thus, a smaller sliding window may
be chosen and in worst case, no identical sequences are found at all). However,
on decompression, the full sliding window must be supported.


3.2 Codes and offsets (extra bits)
-------------------------------------------------------------------------------

On the next stage, the result of the LZ77 analysis is represented as codes and
offsets considering the identical sequences found before (see chapter 3.1):

- The codes 0..255 are called literal codes and represent the corresponding
  original values (i.e. 0x00..0xFF) of single bytes of the input data which
  are not part of an identical sequence.

- The code 256 is an end marker and reserved on this stage (see capter 3.4).

- The codes 257..285 are called length codes and represent a reference to an
  identical sequence where the code depends on the length value of the triple
  (index, distance, length), see below.

If a part of the input data is represented by a reference to an identical
sequence, the corresponding 3 to 258 bytes are omitted (i.e. each part of the
input data is represented by either a literal code or a length code).

While the literal codes are sufficient to represent a single byte of the input
data, references to identical sequences are indicated by a length code in the
range 257..285 but need further representation:

- For length codes in the range 265..284, the length values are subtracted by a
  fixed base and the resulting offset is represented by a fixed number of extra
  bits.

- The distance of the triple (index, distance, length) is represented by a
  second code in the range 0..29 which is called the distance code, see below.

- For distance codes in the range 4..29, the distance values are subtracted by
  a fixed base and the resulting offset is represented by a fixed number of
  extra bits.

In result, a reference to an identical sequence is represented by the following
sequence of codes and offsets:

  <length-code> [ <length-offset> ] <distance-code> [ <distance-offset> ]

The following table specifies the length codes, length bases and number of
extra bits for the length offsets:

  length range  length code range  length base              extra bits
  ------------  -----------------  -----------------------  ----------
         3..10           258..264  3 + code - 258                    0
        11..18           265..268  11 + (code - 265) * 2             1
        19..34           269..272  19 + (code - 269) * 4             2
        35..66           273..276  35 + (code - 273) * 8             3
       67..130           277..280  67 + (code - 277) * 16            4
      131..257           281..284  131 + (code - 281) * 32           5
           258                285  258                               0

The length code can be determined by the maximum code where length >= length
base (e.g. length 34 matches code 272 with length base 19 + (272 - 269) * 4 =
31 but not 273 with length base 35 + (273 - 273) * 8 = 35).

The following table specifies the distance codes, distance bases and number of
extra bits for the distance offsets:

  distance range  distance code range  distance base               extra bits
  --------------  -------------------  --------------------------  ----------
            1..4                 0..3  1 + code                             0
            5..8                 4..5  5 + (code - 4) * 2                   1
           9..16                 6..7  9 + (code - 6) * 4                   2
          17..32                 8..9  17 + (code - 8) * 8                  3
          33..64               10..11  33 + (code - 10) * 16                4
         65..128               12..13  65 + (code - 12) * 32                5
        129..256               14..15  129 + (code - 14) * 64               6
        257..512               16..17  257 + (code - 16) * 128              7
       513..1024               18..19  513 + (code - 18) * 256              8
      1025..2048               20..21  1025 + (code - 20) * 512             9
      2049..4096               22..23  2049 + (code - 22) * 1024           10
      4097..8192               24..25  4097 + (code - 24) * 2048           11
     8193..16384               26..27  8193 + (code - 26) * 4096           12
    16385..32768               28..29  16385 + (code - 28) * 8192          13

The distance code can be determined by the maximum code where distance >=
distance base (e.g. distance 195 matches code 15 with distance base 129 + (15 -
14) * 64 = 193 but not 16 with distance base 257 + (16 - 16) * 128 = 257).

Example:

  The LZ77 compressed data from the example of chapter 3.1 would be represented
  by the following codes and offsets (no length offsets occur here):

  index  literal / length code  distance code  distance offset  input data
  -----  ---------------------  -------------  ---------------  --------------
      0                      0            n/a              n/a  00
      1                      1            n/a              n/a  01
      2                    170            n/a              n/a  AA
      3                    187            n/a              n/a  BB
      4                      0            n/a              n/a  00
      5                      1            n/a              n/a  01
      6                    175            n/a              n/a  AF
      7                    259              2              n/a  00 01 AF 00 01
     12                    190            n/a              n/a  BE
     13                    257              4                1  00 01 AF
     16                    255            n/a              n/a  FF

  For example, the input data sequence 00 01 AF at index 13 is represented by
  the length code 257 (indicating a length of 3 without needing a length
  offset) and the distance code 4 (indicating a distance base of 5), followed
  by a the distance offset 1 which is added to the distance base resulting in
  a distance of 6.

Note that the representation by codes and offsets is still intermediate
information which may be stored at discretion.


3.3 Huffman encoding
-------------------------------------------------------------------------------

All codes from the previous step are encoded by a variable number of bits which
are taken from two different mapping tables:

- One table maps all literal and length codes as well as the code 256 (which is
  used as an end marker, see chapter 3.4) in the range 0..285 to individual bit
  sequences which form a prefix code and should represent a huffman code.

- The other table maps all distance codes in the range 0..29 to individual bit
  sequences which form a prefix code and should represent a huffman code.

The deflate data format specifies that either dynamic mapping tables are used
or fixed mapping tables where the mapping table for distance codes is fixed to
5 bit sequences (the bit sequences 11110 and 11111 must not occur as the codes
30 and 31 are not used) and the mapping table for the literal and length codes
is as follows (the bit sequences 11000110 and 11000110 must not occur as the
codes 286 and 287 are not used):

  code range  length of bit sequence  bit sequence range
  ----------  ----------------------  --------------------
      0..143                       8  00110000..10111111
    144..255                       9  110010000..111111111
    256..279                       7  0000000..0010111
    280..285                       8  11000000..11000101

For dynamic mapping tables, the lengths of the bit sequences of up to 15 bits
should be chosen optimal according to Huffman encoding on compression and are
stored so that they can be reconstructed on decompression (see chapter 3.4).
Codes which never occur do not need a mapped bit sequence and should thus have
a bit length of zero.

How the the optimal length of the bit sequences is determined is not subject
to the deflate data format (in worst case, all bit lengths are set to 15 bits).
However, it is specified how the bit sequences are determined for given lengths
by the following algorithm (let tBitLen[maxCode + 1] by an array of the bit
lengths for each code and maxCode the maximum code value):

  /* count the number of occurrences for each length: */

  for (bitLen = 0; bitLen <= 15; bitLen = bitLen + 1)
  {
       tBitLenCount[bitLen] = 0; 
  }

  for (code = 0; code <= maxCode; code = code + 1)
  {
       tBitLenCount[tBitLen[code]] = tBitLenCount[tBitLen[code]] + 1;
  }

  /* determine the starting bit sequence for each length: */

  tBitLenCount[0] = 0;
  tBitLenSequence[0] = 0;

  for (bitLen = 0; bitLen < 15; bitLen = bitLen + 1)
  {
      tBitLenSequence[bitLen + 1] =
          (tBitLenSequence[bitLen] + tBitLenCount[bitLen]) << 1;
  }

  /* build the mapping table: */

  for (code = 0; code <= maxCode; code = code + 1)
  {
      tBitSequence[code] = tBitLenSequence[tBitLen[code]];

      if (tBitLen[code] > 0)
      {
          tBitLenSequence[tBitLen[code]] = tBitLenSequence[tBitLen[code]] + 1;
      }
  }

Example:

  The following mapping table maps the codes 0, 3, 17 and 21 to bit sequences
  of the length 3, 2, 1 and 2 bits:

  code  tBitLen[code]  tBitSequence[code]
  ----  -------------  ------------------
     0              3  110
     3              2  10
    17              1  0
    21              2  111

Now, given dynamic or fixed mapping tables, the sequence of codes and offsets
from the previous stage (see chapter 3.2) is translated to a sequence of bits
where the codes are encoded by the corresponding bit sequence of the respective
mapping table and the offsets, if given, are represented by the number of extra
bits in big-endian order.

Example:

  The sequence of codes and offsets from the example of chapter 3.2 would be
  represented by the following bit sequences if the fixed mapping table was
  used (the index is omitted from now on):

  bit sequence     literal / length code  distance code  distance offset
  ---------------  ---------------------  -------------  ---------------
  00110000                             0            n/a              n/a
  00110001                             1            n/a              n/a
  110101010                          170            n/a              n/a
  110111011                          187            n/a              n/a
  00110000                             0            n/a              n/a
  00110001                             1            n/a              n/a
  110101111                          175            n/a              n/a
  0000011 00010                      259              2              n/a
  110111110                          190            n/a              n/a
  0000001 00100 1                    257              4                1
  111111111                          255            n/a              n/a


3.4 Block format
-------------------------------------------------------------------------------
