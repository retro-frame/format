2. OVERVIEW
===============================================================================

Deflate is a widly used binary data format for the compression of byte streams
based on LZ77 (Lempel-Ziv 1977) compression and Huffman encoding (i.e. prefix
codes). It was originally designed for the [ZIP] data format and standardized
by [RFC-1951]. The deflate data format is self-delimiting.

This document focuses on the actual data format rather than on the compression
algorithms. Compliance to the data format should result in interoperability
(i.e. one program should be able to decompress a deflate data format which has
been compressed by another program). However, there may be subtle differences
in the implementations which may lead to incompatibility (e.g. an encoding
which was considered valid by the compressor but invalid by the decompressor).
In this document, the rules to encode compressed data may be more strict than
the rules to decode compressed data following the goal that compressed data
can be decompressed by any other program while decompression should accept all
possible encodings as long as they are unambiguous.

Not subject to this document are the compression algorithms. The compression
ratio highly depends on the following choices by the compression algorithms:

- The identical byte sequences during the LZ77 phase (see chapter 4.1).

- The bit lengths of the prefix codes (see chapter 4.3).

- The block sizes and the individual block encoding methods (see chapter 4.5).

In other words, it would be possible to create a valid deflate data format with
a poor compression ratio (even worse, the compressed data size may be larger
than the uncompressed data size). Thus, it is subject to the implementations to
select appropriate algorithms in order to achieve a good compression ratio.



3. DEFINITIONS
===============================================================================


3.1 Value
-------------------------------------------------------------------------------

A 'VALUE' is a number which represents a single byte of the input data or the
actual length respectively distance of the reference to an identical byte
sequence. The value of a single byte of the input data is represented in
hexadecimal notation while the value of a length or distance is represented in
decimal notation.


3.2 Base / offset
-------------------------------------------------------------------------------

A 'BASE' is a predefined length or distance VALUE. An 'OFFSET' is a summand of
a length or distance VALUE so that VALUE = BASE + OFFSET. While the BASE is an
implicit value, the OFFSET is represented in the compressed data as extra bits.


3.3 Symbol
-------------------------------------------------------------------------------

A 'SYMBOL' is a number which is used for intermediate representation of

- single bytes of the input data,
- a range of length respectively distance VALUES which use the same BASE,
- a block end marker or
- a single bit length respectively a sequence of identical bit lengths.

Symbols are represented by a number in decimal representation which is prefixed
by one, two or three commercial at signs ('@'):

- @<number> represents a literal, block end marker or length (LIT) symbol
- @@<number> represents a distance (DIST) symbol
- @@@<number> represents a prefix code bit length (CLEN) symbol

When a symbol used in a numeric expression, the number of the symbol is casted
to a VALUE implicitly (e.g. @@12 - 3 = 9).


3.4 Bit sequence / bit length
-------------------------------------------------------------------------------

A 'BIT SEQUENCE' is the binary representation of a number with a defined number
of bits in a defined order which represents an atomic unit of the deflate data
format. The 'BIT LENGTH' is the number of bits of a BIT SEQUENCE.

Note that the bit length is not necessarily a multiple of 8 and that in the
textual representation the most significant (i.e. high) bits always come first
while the encoding of bit seqeuences in bytes will reverse the bit order (see
chapter 4.4). On decompression, the bit length must be known in advance except
for PREFIX CODES where the bit length can be determined implicitly.


3.5 Prefix code
-------------------------------------------------------------------------------

A 'PREFIX CODE' is a BIT SEQUENCE which distinctly represents a SYMBOL where
the BIT LENGTH is variable but can be determined implicitly. Although it is
intented that the PREFIX CODES are Huffman codes (i.e. optimal regarding the
BIT LENGTH), the term Huffman code is avoided in this documemt as the deflate
data format relies on the prefix code property rather than on the Huffman code
property.



4. DEFLATE PHASES
===============================================================================


4.1 Identifying identical sequences (LZ77 analysis)
-------------------------------------------------------------------------------

The initial processing of the input data (given as a UINT-8 sequence of bytes)
is the identification of identical (i.e. duplicate) sequences of a length from
3 to 258 bytes within a sliding window of 32768 bytes according to the LZ77
compression (the algorithms are not subject to this description of the data
format):

                          +------------------------------+
                          |  32768 bytes sliding window  |
  +-----------------------+------------------------------+------------------+
  |  input data (UINT-8)                 <length>         <length>          |
  +--------------------------------------^----------------^-----------------+
                                         |   <distance>   | current index
                                         +----------------+

The position of the identical sequence within the sliding window is referenced
by the backward distance relative to the current index (i.e. the byte preceding
the current index has distance 1 and the maximum distance is 32768). Within the
first 32768 bytes of the input data, the sliding window shall be clipped (i.e.
the distance must not exceed the input data). While the sequence must start
within the sliding window, it may overlap with the identical sequence starting
from the current index (e.g. a sequence with a distance of 4 and a length of 9
has an overlap of five bytes with the sequence at the current index).

All references to identical sequences given by the triple

  (index, distance, length)

are intermediate information in this phase and may be stored at discretion. No
more than one reference shall exist for each index. If more than one sequence
was found in the sliding window, the sequence with the maximum length should be
chosen (if the maximum length was found multiple times, the smallest distance
should be favored).

Example:

  index  input data  distance  length  comment
  -----  ----------  --------  ------  --------------------------------
      0          00       n/a     n/a  identical sequence not possible
      1          01       n/a     n/a  no identical sequence
      2          AA       n/a     n/a  no identical sequence
      3          BB       n/a     n/a  no identical sequence
      4          00       n/a     n/a  sequence 00 01 is too short
      5          01       n/a     n/a  sequence 01 is too short
      6          AF       n/a     n/a  no identical sequence
      7          00         3       5  sequence 00 01 AF 00 01 overlaps
      8          01       n/a     n/a  part of identical sequence
      9          AF       n/a     n/a  part of identical sequence
     10          00       n/a     n/a  part of identical sequence
     11          01       n/a     n/a  part of identical sequence
     12          BE       n/a     n/a  no identical sequence
     13          00         6       3  favor smaller distance
     14          01       n/a     n/a  part of identical sequence
     15          AF       n/a     n/a  part of identical sequence
     16          FF       n/a     n/a  no identical sequence

  As a result, the identical sequences are (7, 3, 5) and (13, 6, 3).

Note that LZ77 analysis is always performed on the entire input data, even if
the data is processed in smaller buffers and regardless of the block format
determined later (see chapter 4.5). However, no references to other input data
must be used, even if other input data may be immediately preceding (e.g. in a
file).

On compression, in order to comply with the data format, it is not required to
find all or the optimal identical sequences (thus, a smaller sliding window may
be chosen and in worst case, no identical sequences are found at all). However,
on decompression, the full sliding window must be supported.


4.2 Representation by symbols and offsets
-------------------------------------------------------------------------------

In the next phase, the result of the LZ77 analysis is represented as symbols
and offsets considering the identical sequences found before (see chapter 4.1):

- The symbols @0..@255 are called literal codes and represent the corresponding
  original values (i.e. 0x00..0xFF) of single bytes of the input data which
  are not part of an identical sequence.

- The symbol @256 is a block end marker (see chapter 4.5) and reserved in this
  phase.

- The symbols @257..@285 are called length symbols and represent a reference to
  an identical sequence where the symbols depends on the length value of the
  triple (index, distance, length), see below.

If a part of the input data is represented by a reference to an identical
sequence, the corresponding 3 to 258 bytes are omitted (i.e. each part of the
input data is represented by either a literal or a length symbol).

While a single literal symbol is sufficient to represent a single byte of the
input data, references to identical sequences are indicated by a length symbol
in the range @257..@285 but need further representation:

- For length symbols in the range @265..@284, the length values are split into
  a fixed base and an offset which is represented by a fixed number of extra
  bits.

- The distance of the triple (index, distance, length) is represented by a
  second symbol in the range @@0..@@29 which is called the distance symbol,
  see below.

- For distance symbols in the range @@4..@@29, the distance values are split
  into a fixed base and an offset which is represented by a fixed number of
  extra bits.

In result, a reference to an identical sequence is represented by the following
sequence of symbols and offsets:

  <length-symbol> [ <length-offset> ] <distance-symbol> [ <distance-offset> ]

The following table specifies the length symbols, length bases and length
offsets, depending on the length values:

  length value  length symbol  length base                length offset
  ------------  -------------  -------------------------  -------------
         3..10     @257..@264  3 + symbol - 257                       0
        11..18     @265..@268  11 + (symbol - 265) * 2             0..1
        19..34     @269..@272  19 + (symbol - 269) * 4             0..3
        35..66     @273..@276  35 + (symbol - 273) * 8             0..7
       67..130     @277..@280  67 + (symbol - 277) * 16           0..15
      131..257     @281..@284  131 + (symbol - 281) * 32          0..31
           258           @285  258                                    0

On compression, the length symbol shall be determined by finding the maximum
symbol where length value is greater or equal than the length base (e.g. length
value 34 matches symbol @272 with length base 19 + (@272 - 269) * 4 = 31 but
not symbol @273 with length base 35 + (@273 - 273) * 8 = 35). On decompression,
the length base is calculated for each recognized symbol as given (as a special
case, the length value 258, which should be represented by length symbol @285,
may also result from the length symbol @284 with offset 31).

The following table specifies the distance symbols, distance bases and distance
offsets, depending on the distance values:

  distance value  distance symbol  distance base                distance offset
  --------------  ---------------  ---------------------------  ---------------
            1..4         @@0..@@3  1 + symbol                                 0
            5..8         @@4..@@5  5 + (symbol - 4) * 2                    0..1
           9..16         @@6..@@7  9 + (symbol - 6) * 4                    0..3
          17..32         @@8..@@9  17 + (symbol - 8) * 8                   0..7
          33..64       @@10..@@11  33 + (symbol - 10) * 16                0..15
         65..128       @@12..@@13  65 + (symbol - 12) * 32                0..31
        129..256       @@14..@@15  129 + (symbol - 14) * 64               0..63
        257..512       @@16..@@17  257 + (symbol - 16) * 128             0..127
       513..1024       @@18..@@19  513 + (symbol - 18) * 256             0..255
      1025..2048       @@20..@@21  1025 + (symbol - 20) * 512            0..511
      2049..4096       @@22..@@23  2049 + (symbol - 22) * 1024          0..1023
      4097..8192       @@24..@@25  4097 + (symbol - 24) * 2048          0..2047
     8193..16384       @@26..@@27  8193 + (symbol - 26) * 4096          0..4095
    16385..32768       @@28..@@29  16385 + (symbol - 28) * 8192         0..8191

On compression, the distance  symbol shall be determined by finding the maximum
symbol where distance value is greater or equal than the distance base (e.g.
distance 99 matches symbol @@13 with distance base 65 + (@@13 - 12) * 32 = 97
but not symbol @@14 with distance base 129 + (@@14 - 14) * 64 = 129). On
decompression, the distance is calculated for each recognized symbol as given.

Example:

  The LZ77 compressed data from the example of chapter 4.1 would be represented
  by the following codes and offsets (no length offsets occur here):

  index  input data  literal / length symbol  distance symbol  distance offset
  -----  ----------  -----------------------  ---------------  ---------------
      0  00                               @0              n/a              n/a
      1  01                               @1              n/a              n/a
      2  AA                             @170              n/a              n/a
      3  BB                             @187              n/a              n/a
      4  00                               @0              n/a              n/a
      5  01                               @1              n/a              n/a
      6  AF                             @175              n/a              n/a
      7  (7, 3, 5)                      @259              @@2              n/a
     12  BE                             @190              n/a              n/a
     13  (13, 6, 3)                     @257              @@4                1
     16  FF                             @255              n/a              n/a

  For example, the input data sequence 00 01 AF at index 13 is represented by
  the length symbol @257 (indicating a length of 3 without needing a length
  offset) and the distance symbol @@4 (indicating a distance base of 5),
  followed by the distance offset 1 which is added to the distance base
  resulting in a distance of 6.

Note that the representation by symbols and offsets is still intermediate
information which may be stored at discretion.


4.3 Encoding as bit sequences
-------------------------------------------------------------------------------

All symbols from the previous phase are encoded by bit sequences which are
taken from two different mapping tables:

- One table maps all literal and length symbols as well as the symbol @256
  (which is a block end marker, see chapter 4.5) in the range @0..@285 to bit
  sequences which must form a valid prefix code.

- The other table maps all distance symbols in the range @@0..@@29 to bit
  sequences which must form a valid prefix code.

The deflate data format specifies that either dynamic mapping tables or the
fixed mapping tables are used.

The following table specifies the fixed mapping for the literal and length
symbols:

  literal / length symbol  bit length   bit sequence (prefix code)
  -----------------------  -----------  --------------------------
                 @0..@143            8  00110000..10111111
               @144..@255            9  110010000..111111111
               @256..@279            7  0000000..0010111
               @280..@285            8  11000000..11000101

The following table specifies the fixed mapping for the distance symbols:

  distance symbol  bit length  bit sequence (prefix code)
  ---------------  ----------  --------------------------
        @@0..@@29           5  00000..11101

For dynamic mapping tables, a bit length in the range 0..15 must be chosen for
each symbol. A bit length of 0 means that a symbol cannot be represented by a
bit sequene. Thus, symbols which are actually used must not have a bit length
of 0. How the the optimal lengths of the symbols is determined is not subject
to the deflate data format (in worst case, all bit lengths are set to 15 bits).

Given the individual bit lengths, the bit sequences (i.e. prefix codes) for the
literal / length symbols as well as those for the distance symbols must be
determined by the following algorithm (let maxSymbol the maximum symbol value
and tBitLen[maxSymbol + 1] an array of the bit lengths for each symbol while
tPrefixCode[maxSymbol + 1] receives the resulting bit sequences of the prefix
code as unsigned integers):

  /* count the number of occurrences for each bit length: */

  for (bitLen = 0; bitLen <= 15; bitLen = bitLen + 1)
  {
      tBitLenCount[bitLen] = 0; 
  }

  for (symbol = 0; symbol <= maxSymbol; symbol = symbol + 1)
  {
      tBitLenCount[tBitLen[symbol]] = tBitLenCount[tBitLen[symbol]] + 1;
  }

  /* determine the starting bit sequence for each bit length: */

  tBitLenCount[0] = 0;
  tBitSequence[0] = 0;

  for (bitLen = 1; bitLen <= 15; bitLen = bitLen + 1)
  {
      tBitSequence[bitLen] =
          (tBitSequence[bitLen - 1] + tBitLenCount[bitLen - 1]) << 1;
  }

  /* build the mapping table: */

  for (symbol = 0; symbol <= maxSymbol; symbol = symbol + 1)
  {
      bitLen = tBitLen[symbol];

      tPrefixCode[symbol] = tBitSequence[bitLen];

      if (bitLen > 0)
      {
          tBitSequence[bitLen] = tBitSequence[bitLen] + 1;
      }
  }

Note that, on compression, overflows must be avoided (e.g. if more than two
symbols are given but two symbols have a bit length of one bit, or if 14
symbols have a consecutive bit length from 1..14, only two bit sequences are
left for a bit length of 15). On decompression, such cases shall be considered
an invalid format.

On compression, maxSymbol shall be the maximum value of the defined symbols
(i.e. 285 for the literal / length symbols and 29 for the distance symbols),
on decompression, undefined symbols may occur from the input (see chapter 4.4),
resulting in maxSymbol up to 287 for the literal / length symbols and 31 for
the distance symbols. In this case, the undefined symbols would participate in
the calculation of the prefix codes but must never be used (i.e. if a prefix
code of an undefined symbol occured, the format shall be considered invalid).

Example:

  The following mapping table shows for the symbols @0, @3, @17 and @21 with
  given bit lengths 3, 2, 1 and 2 bits the resulting prefix codes as unsigned
  integers (in binary notation) as well as bit sequences:

  symbol  tBitLen[symbol]  tPrefixCode[symbol]  bit sequence (prefix code)
  ------  ---------------  -------------------  --------------------------
      @0                3           0b00000110  110
      @3                2           0b00000010  10
     @17                1           0b00000000  0
     @21                2           0b00000111  111

Offsets, if given, are encode by a fixed number of extra bits. The bit sequence
is the binary representation of the offset value in reversed order (i.e. least
significant bits come first) and the bit length is the minimum number of bits
capable to represent the full range of offsets as specified for each symbol
(e.g. for the symbol @279, the range of offsets is 0..15, so that 4 extra bits
are used, and an offset of value 5 would be represented as 1010).

Example:

  The sequence of codes and offsets from the example of chapter 4.2 would be
  represented by the following bit sequences if the fixed mapping tables are
  used (the index is omitted from now on):

  literal / length symbol  distance symbol  distance offset  bit sequences
  -----------------------  ---------------  ---------------  ---------------
                       @0              n/a              n/a  00110000
                       @1              n/a              n/a  00110001
                     @170              n/a              n/a  110101010
                     @187              n/a              n/a  110111011
                       @0              n/a              n/a  00110000
                       @1              n/a              n/a  00110001
                     @175              n/a              n/a  110101111
                     @259              @@2              n/a  0000011 00010
                     @190              n/a              n/a  110111110
                     @257              @@4                1  0000001 00100 1
                     @255              n/a              n/a  111111111


4.4 Dynamic mapping table representation
-------------------------------------------------------------------------------

If dynamic mapping tables are used, they are stored in the following manner so
that they can be reconstructed on decompression.

Both mapping tables, the literal / length symbol mapping table and the distance
symbol table, are defined by the individual bit lengths of the prefix codes of
the symbols in ascending order of the symbol values.

As an intermediate step, each mapping table is represented by sequences of bit
lengths in the range 0..15 and the length of each sequence (i.e. the number of
bit lengths) is determined as follows:

- For the literal / length symbol mapping table, trailing bit lengths of 0 may
  be truncated as long as at least 257 bit lengths remain in the sequence. On
  decompression, bit lengths for the undefined symbols @286 and @287 may occur
  which would participate in the prefix code calculation but must never be used
  (see chapter 4.3). Thus, a sequence of bit lengths with 257..286 elements on
  compression and 257..288 elements decompression is used. The number of bit
  lengths in the sequence is denoted by #LIT.

- For the distance symbol mapping table, trailing bit lengths of 0 may be
  truncated as long as at least one bit length remains in the sequence. On
  decompression, bit lengths for the undefined symbols @@30 and @@31 may occur
  which would participate in the prefix code calculation but must never be used
  (see chapter 4.3). Thus, a sequence of bit lengths with 1..30 elements on
  compression and 1..32 on elements decompression is used. The number of bit
  lengths in the sequence is denoted by #DIST.

Now, both sequences are concatenated, resulting in a single sequence of bit
lengths (i.e. 258..316 elements on compression and 258..320 elements on
decompression), which is translated to a sequence of prefix code bit length
(CLEN) symbols as follows:

- A single bit length is represented by a CLEN symbol of the same value (e.g.
  a bit length of 13 is represtented by the symbol @@@13).

- 3..6 repeats of a bit length may be represented by the symbol @@@16 and the
  number of bit lengths is represented by an offset using the base 3. The
  symbol @@@16 must not be the first symbol of the sequence as there is no
  bit length yet to be repeated. However, the bit length to be repeated may
  result from any CLEN symbol (e.g. a sequence of 14 bit lengths of the value
  6 may be represented by @@@6, @@@16, 3, @@@16, 3, @@@16, 1).

- 3..10 bit lengths of the value 0 may be represented by the symbol @@@17 and
  the number of bit lengths is represented by an offset using the base 3 (e.g.
  8 bit lengths of the value 0 may be represented by @@@17, 5).

- 11..138 bit lengths of the value 0 may be represented by the symbol @@@18 and
  the number of bit lengths is represented by an offset using the base 11 (e.g.
  28 bit lengths of the value 0 may be represented by @@@18, 17).

The symbols and offsets are encoded as bit sequences (i.e. prefix codes and
extra bits) just like the input data (see chapter 4.3) except that a CLEN
mapping table is used, rather than one literal / length and one distance
mapping table, to represent the CLEN symbols and that the bit lengths of the
prefix codes in that table must be in the range 0..7 rather than 0..15.

The bit lengths of the CLEN mapping table are represented as the sequence of
their values in the following order of the CLEN symbols:

  @@@16, @@@17, @@@18, @@@0, @@@8, @@@7, @@@9, @@@6, @@@10, @@@5, @@@11, @@@4,
  @@@12, @@@3, @@@13, @@@2, @@@14, @@@1, @@@15

Trailing bit lengths of 0 may be truncated as long as at least 4 bit lengths
remain in the sequence (i.e. the minimal sequence to represent the bit lengths
of a CLEN mapping table would be @@@16, @@@17, @@@18, @@@0 which can, however,
never occur as those symbols alone can only represent bit lengths of 0). The
number of bit lengths of the CLEN mapping table is denoted by #CLEN.

#LIT, #DEST, #CLEN, the bit lengths of the CLEN mapping table and the bit
sequences of the encoded bit lengths result in the following representation:

- #LIT - 257, encoded by 5 bits (i.e. LLIT is in the range 257..288) in
  reversed order (i.e. least significant bits come first).

- #DIST - 1, encoded by 5 bits (i.e. LDIST is in the range 1..32) in reversed
  order (i.e. least significant bits come first).

- #CLEN - 4, encoded by 4 bits (i.e. LCLEN is in the range 4..19) in reversed
  order (i.e. least significant bits come first).

- #CLEN bit lengths of the CLEN mapping table in the given order, each encoded
  by 3 bits (i.e. each bit length is in the range 0..7), in reversed order
  (i.e. least significant bits come first).

- The bit sequences of the encoded bit lengths, using the CLEN mapping table,
  to encode #LIT + #DIST bit lengths. Note that if the last symbol is @@@16,
  @@@17 or @@@18, more bit lengths may result than actually required. In this
  case, the unnecessary bit lengths shall be ignored (i.e. the number of bit
  lengths produced by this symbol is clipped). However, on compression, this
  case shall be avoided (as a consequence, 2 or 3 identical bit lengths at the
  end of the sequence cannot be compressed using the symbol @@@16).

Example:

  The input data only consists of ASCII encoded digits (i.e. 0x30..0x39) and LF
  (0x0A) but no identical sequences are found. The literal symbols @48..@53 are
  encoded using a bit length of 3, @54 and @55 using a bit length of 4 and @56,
  @57, @10 and the mandatory block end marker @256 using a bit length of 5.

  The resulting bit lengths are (#LIT = 257, #DIST = 1):

  - 0 for @0..@9 (10 times)
  - 5 for @10
  - 0 for @11..47 (37 times)
  - 3 for @48..@53 (6 times)
  - 4 for @54..@55
  - 5 for @56..@57
  - 0 for @58..@255 (198 times)
  - 5 for @256
  - 0 for @@0

  This can be represented by the following sequences of CLEN symbols and
  offsets:

    @@@17, 7, @@@5, @@@18, 26, @@@3, @@@16, 2, @@@4, @@@4, @@@5, @@@5, @@@18,
    127, @@@18, 49, @@@5, @@@0

  The symbols @@@4, @@@5 and @@@18 might be encoded by a bit length of 2 while
  the remaining symbols might be encoded by a bit length of 4. The resulting
  prefix codes are:

    CLEN symbol  bit length  prefix code
    -----------  ----------  -----------
    @@@0                  4  1100
    @@@3                  4  1101
    @@@4                  2  00
    @@@5                  2  01
    @@@16                 4  1110
    @@@17                 4  1111
    @@@18                 2  10

  The resulting entire output as bit sequences is as follows (#CLEN = 14):

    00000 00000 0111 001 001 010 001 000 000 000 000 000 010 000 010 000 001
    1111 111 01 10 0101100 1101 1110 01 00 00 01 01 10 1111111 10 1000110 01
    1100


4.5 Block format
-------------------------------------------------------------------------------

Eventually, the input data is split into one or more blocks where each block
uses one of the following encoding methods:

- Compressed blocks using dynamic mapping tables
- Compressed blocks using fixed mapping tables
- Uncompressed blocks

How the size of a block and the encoding methods are determined is not subject
to the deflate data format. In general, the size of a compressed block using
either dynamic or fixed mapping tables may be maintained during processing and
if compression ratio would decrease, the current block may be terminated and a
new block may be created. Uncompressed blocks should be used only if the input
data cannot be compressed (i.e. the compressed size would be greater or equal
than the uncompressed size). Note that the LZ77 analysis (see chapter 4.1) is
independent from the blocks chosen.

Each block has a header of 3 bits which immediately follows the last bit of a
previous block, if given:

- The least significand bit is a flag which indicates the last block if set to
  1. Thus, the deflate data format is self delimiting.

- The two most significand bits represent the encoding method (the bit sequence
  11 is invalid):

  00: uncompressed block
  01: compressed blocks using fixed mapping tables
  10: compressed blocks using dynamic mapping tables

The block header is encoded by a bit sequence in reversed order (i.e. least
significant bits come first). Note that the header may also be processed by two
individual bit sequences of the lengths 1 for the last block flag and 2 for the
encoding method.

Compressed blocks immediately start after the block header. If dynamic mapping
tables are used, the mapping table representation (see chapter 4.4) is stored
first. Then, regardless which mapping tables are used, the prefix encoded
symbols and extra bits (see chapter 4.3) are stored bit sequence by bit
sequence and eventually the block is terminated by the bit sequence which
represents the symbol @256 (thus, this code must not have a bit length of 0).

The bit sequences are packed into bytes starting on the least significant bit
of the byte. Note that this will reverse the bit order bytewise.

Example:

  The start of a compressed block, which is not the final block, using the
  mapping table representation from the example of chapter 4.4, would result
  in the following bit sequences:

    001 00000 00000 0111 001 001 010 001 000 000 000 000 000 010 000 010 000
    001 1111 111 01 10 0101100 1101 1110 01 00 00 01 01 10 1111111 10 1000110
    01 1100

  The bit sequences are now grouped by 8 bits:

    00100000 00000011 10010010 10001000 00000000 00000100 00010000
    00111111 11011001 01100110 11110010 00001011 01111111 10100011
    0011100

  This results in the following byte sequence (note that the last group of bits
  is incomplete so that the most significant bit of that byte, represented by a
  question mark '?', depends on the following data):

    00000100 11000000 01001001 00010001 00000000 00100000 00001000
    11111100 10011011 01100110 01001111 11010000 11111110 11000101
    ?0011100

While compressed blocks have no size limit, uncompressed blocks are limited to
65535 bytes. If an uncompressed block is indicated by the block header and the
last bit of the block header does not align on a byte boundary, padding bits
are inserted until the next byte boundary is reached (those paddings bits shall
be set to 0 on compression and ignored on decompression).

Then, the next 4 bytes represent the the size of the uncompressed data by two
UINT-16 values in little-endian order where the secont value is the one's
complement of the size and size bytes of uncompressed input data follow:

  +---+---+---+---+---------------------------------------------+
  |  size | ~SIZE |  uncompressed block of input data (UINT-8)  |
  +---+---+---+---+---------------------------------------------+

Example:

  The input data 0xA0 0xCD 0x8F would be represented by an uncompressed block,
  which is only block (i.e. the first as well as the last block), by the
  following byte sequence:

  0x01 0x03 0x00 0xFC 0xFF 0xA0 0xCD 0x8F

Although not explicitly stated by [RFC-1951], size should be greater than 0 on
compression except if no input data is given at all and an uncompressed block
is explicitly required (in general, the shortest deflate sequence to represent
empty input data, is a compressed block using fixed mapping tables with the
block end marker as the only symbol). However, a size of 0 shall be recognized
on decompression. If, on decompression, the one's complement of size (~SIZE)
does not match the size (i.e. size XOR ~SIZE is not 0xFFFF), decompression may
be continued but a warning should be given.

Note that if a block is uncompressed, the results of all previous phases are
discarded. However, the input data which is stored as uncompressed data may
still be part of the sliding window for LZ77 analysis of the next block(s).
